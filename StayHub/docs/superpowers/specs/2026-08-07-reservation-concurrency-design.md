# StayHub 동시 예약 방지 디자인

## 목표

같은 객실과 겹치는 날짜에 여러 예약 요청이 동시에 도착해도 정확히 한 요청만 성공하도록 보장한다. 인접하지만 겹치지 않는 예약과 기존 취소·조회·상태 전환 동작은 유지한다.

## 원인

현재 예약 생성은 중복 예약 조회와 예약 저장이 서로 다른 DB 작업이다. 두 요청이 중복 조회를 동시에 통과하면 같은 객실과 날짜에 두 예약이 생성될 수 있다. 기존 복합 인덱스는 조회 성능만 개선하며 날짜 범위의 겹침을 unique 제약으로 막지 못한다.

## 선택한 방식

MongoDB 트랜잭션 안에서 객실 문서의 `reservationVersion`을 증가시켜 같은 객실의 예약 요청이 반드시 동일 문서에 쓰도록 한다. 이후 같은 세션으로 겹치는 예약을 조회하고 예약을 생성한다.

동시 요청이 같은 객실 문서를 갱신하면 MongoDB가 한 트랜잭션에 쓰기 충돌을 발생시킨다. Mongoose의 `withTransaction` 재시도 후 최신 스냅샷에서 중복 예약이 발견되면 HTTP 409용 `AppError`를 반환한다.

## 데이터 변경

- `Room.reservationVersion`: 숫자, 기본값 0, API 사용자에게 별도 의미를 요구하지 않는다.
- 기존 객실은 필드가 없어도 `$inc` 시 자동으로 숫자 값이 생성되므로 마이그레이션이 필요 없다.

## 저장소 인터페이스

- `incrementRoomReservationVersion(roomId, session)`: 객실 버전을 원자적으로 증가시키고 갱신된 객실을 반환한다.
- `findOverlappingReservation(roomId, checkInDate, checkOutDate, session)`: 선택적 세션으로 조회한다.
- `createReservation(reservationData, session)`: 선택적 세션으로 한 건을 생성하고 생성된 문서를 반환한다.

## 서비스 흐름

1. 필수 값과 날짜 형식을 검증한다.
2. MongoDB 세션을 시작한다.
3. 트랜잭션 안에서 객실 예약 버전을 증가시키며 객실 존재 여부를 확인한다.
4. 객실 최대 인원과 가격을 검증한다.
5. 같은 세션으로 겹치는 `confirmed` 또는 `checkedIn` 예약을 조회한다.
6. 겹침이 있으면 409 오류를 발생시킨다.
7. 겹침이 없으면 같은 세션으로 예약을 생성한다.
8. 성공 또는 실패 여부와 관계없이 세션을 종료한다.

입력값 검증처럼 트랜잭션과 무관한 검사는 가능한 한 세션 생성 전에 수행한다. 존재하지 않는 객실은 404, 중복 예약은 기존과 동일한 409 메시지를 유지한다.

## 재시도와 오류 처리

- 트랜잭션 재시도는 Mongoose/MongoDB 드라이버의 `withTransaction` 동작을 사용한다.
- 애플리케이션에서 무한 재시도 루프를 추가하지 않는다.
- 쓰기 충돌 재시도 후 중복이 확인되면 정상적인 비즈니스 오류 409로 처리한다.
- 트랜잭션을 지원하지 않는 MongoDB 배포 환경에서는 서버 오류가 기록되며, 현재 `mongodb+srv` 배포 환경을 운영 전제 조건으로 둔다.

## 테스트

- 트랜잭션 콜백 안에서 객실 버전 증가, 중복 조회, 예약 생성에 동일 세션이 전달되는지 테스트한다.
- 겹치는 예약이 있으면 생성하지 않고 409를 반환하는지 테스트한다.
- 겹치지 않는 인접 날짜는 허용하는 기존 범위 조건을 테스트한다.
- 세션이 성공과 오류 양쪽에서 종료되는지 테스트한다.
- 기존 이미지 계약 테스트와 백엔드 문법 검사를 함께 실행한다.

## 범위 제외

- 결제 처리와 예약 보류 만료는 추가하지 않는다.
- Redis 또는 별도의 숙박일 컬렉션은 추가하지 않는다.
- 취소 시 `reservationVersion`을 되돌리지 않는다. 버전은 잠금 충돌 유도용 단조 증가 값이다.
- 프론트엔드 화면과 API 형식은 변경하지 않는다.
